# Конспект к ЛР 5–8

## ЛР 5. Файлы и исключения

`Path` — путь к файлу. `Files.readAllLines(path, StandardCharsets.UTF_8)` читает строки с явно заданной кодировкой. UTF-8 нужен, чтобы русские буквы читались одинаково на разных компьютерах. Для этой учебной задачи файл целиком помещается в память.

Ошибка источника означает, что файла нет или его нельзя прочитать: результата чтения не существует. Ошибка записи означает, что файл читается, но одна строка неправильная. Поэтому IOException оборачивается в DataLoadingException, а ошибки строк попадают в список ValidationError. `getCause()` позволяет узнать исходную причину.

`throw` выбрасывает конкретное исключение. `throws` указывает в объявлении метода, какие проверяемые исключения могут выйти наружу. IOException — checked exception, его нужно поймать или объявить. RuntimeException и его потомки — unchecked. NumberFormatException возникает при Integer.parseInt("bad").

Алгоритм loader: прочитать файл → проверить заголовок → пропустить пустые строки → split(";", -1) → проверить число полей и пустоту → преобразовать часы и статус → проверить часы → создать задачу. `-1` сохраняет последнее пустое поле: строка с пустым статусом должна дать ошибку status, а не потерять столбец. Номер строки — индекс в списке плюс один.

Почему не catch(Exception) вокруг всего файла? Так можно случайно скрыть ошибку программы, принять её за ошибку данных и остановить обработку остальных строк. Здесь отдельно перехватываются IOException, NumberFormatException и IllegalArgumentException для enum. В ЛР 8 catch(Exception) оправдан контрактом пользовательской TaskFunction, но InterruptedException обработан отдельно.

`@TempDir` создаёт временный каталог для теста; тест сам записывает необходимые файлы. Такие данные не нужно добавлять в Git. try-with-resources закрывает открытый ресурс автоматически; readAllLines сам управляет открываемым файлом, поэтому дополнительный ресурс в loader не создаётся.

Показать на защите: смешанный файл и номера ошибок, кириллицу, неправильный статус, getCause() у отсутствующего файла. Пример корректной строки: `T-101;Подготовить релиз;backend;8;READY`.

## ЛР 6. Коллекции и дженерики

`T` — параметр типа. В Box<String> вместо T используется String, поэтому set(10) не компилируется. При get() не нужно приводить Object к String. Raw type вроде `Box box` теряет эту защиту; используем `Box<String>`.

Стек работает по LIFO: последним положили — первым извлекли. После push(10), push(20) peek() возвращает 20 и не меняет размер; pop() возвращает 20 и удаляет его. Пустой pop/peek — NoSuchElementException, null в нашем контракте запрещён.

ArrayList хранит элементы в массиве. Добавление в конец — амортизированное O(1), иногда при расширении O(n). Удаление последнего, peek, size, isEmpty — O(1). Список занимает O(n) памяти. Готовый ArrayDeque обычно удобен для прикладного стека, но здесь требуется собственный учебный класс.

List хранит последовательность и допускает повторы. Set хранит уникальные элементы. Map связывает ключ и значение. EnumMap используется для статусов, LinkedHashSet — для категорий с сохранением порядка появления. Равенство элементов Set зависит от equals/hashCode; у String они уже согласованы.

Сортируется `new ArrayList<>(tasks)`: изменение порядка копии не меняет исходный список. Копия неглубокая, но ProjectTask неизменяемый. Comparator сначала сравнивает часы через Integer.compare, при равенстве — id через compareTo. Вычитание чисел может переполниться. Сортировка O(n log n), подсчёт и выделение категорий — O(n) в обычном случае.

Показать на защите: два типа Box и Stack, запрещённую строку в комментарии теста, равную трудоёмкость задач с разными id.

## ЛР 7. Stream API

Лямбда `task -> task.getStatus() == status` — краткая реализация функции проверки. Функциональный интерфейс имеет один абстрактный метод. Method reference `ProjectTask::getCategory` эквивалентен `task -> task.getCategory()`.

Stream — конвейер обработки, а не коллекция для хранения. Его нельзя повторно использовать после терминальной операции. filter, map, sorted — промежуточные операции; toList, collect, max — терминальные. Промежуточные операции ленивые: обработка начинается, когда запрашивается терминальный результат. sorted требует собрать элементы для сортировки.

filter оставляет подходящие элементы; map преобразует каждый; sorted задаёт порядок; groupingBy собирает группы; counting считает количество в каждой. `groupingBy(..., TreeMap::new, counting())` даёт Map<String, Long> с алфавитным порядком ключей.

Нормализация категории: trim и toLowerCase(Locale.ROOT). В этой реализации " QA " и "qa" — одна группа. В списке нормализованных категорий повторы сохраняются, потому что distinct условием не требуется. В ЛР 6 категории сохраняются с исходным регистром; это явно описано в README.

Optional сообщает, что результата может не быть. max пустого списка возвращает Optional.empty(). В тесте известного непустого списка используется orElseThrow(), а для пустого — isEmpty(). Нельзя вызывать get() без проверки.

Мы не добавляем элементы во внешний ArrayList из forEach: результат собирается через toList/collect. Входной список не меняется. Stream.toList возвращает немодифицируемый список. parallelStream не используется.

Показать на защите: пустой Optional, нормализацию, сортировку по двум ключам и тест неизменности исходного списка.

## ЛР 8. Конкурентная обработка

Задача — работа, которую нужно выполнить. Поток — исполнитель. ExecutorService управляет пулом потоков и принимает задачи. Callable<R> возвращает R и может выбрасывать исключение; Runnable не возвращает результат. submit возвращает Future, по которому можно дождаться результата через get().

Алгоритм: отправить все задачи → сохранить futures в порядке входа → пройти futures в том же порядке → собрать TaskResult с индексом. Даже если второй файл прочитан раньше первого, в результирующем списке он остаётся вторым. Ожидание первого future не мешает другим задачам выполняться в пуле.

Рабочие задачи возвращают значения и не записывают их в общий ArrayList. Итоговый список заполняет только вызывающий поток. Это избавляет от гонки при добавлении результатов. Переданная function должна быть безопасна для одновременных вызовов; TaskFileCounter не имеет изменяемых полей.

ExecutionException оборачивает ошибку задачи; getCause() даёт причину. Обычная ошибка превращается в TaskResult.failure(index, error). Error не маскируется как ошибка данных. Прерывание — запрос остановки, его нельзя молча игнорировать. Concurrent-метод передаёт InterruptedException наружу и отменяет futures; sequential-метод восстанавливает флаг и выбрасывает unchecked-исключение, потому что его заданная сигнатура не содержит throws.

Владелец executor — создавший его код. Он вызывает shutdown в finally. BatchProcessor получает чужой executor и не закрывает его. shutdown перестаёт принимать новые задачи, но даёт уже отправленным закончить работу. shutdownNow пытается прервать незавершённые задачи. awaitTermination ожидает завершения ограниченное время. Отмена с true просит прервать поток, но не может принудительно остановить код, игнорирующий interruption.

`count++` состоит из чтения, увеличения и записи; два потока могут потерять обновление. volatile делает изменения видимыми, но не превращает всю эту операцию в атомарную.

Тест порядка использует CountDownLatch: первая задача ждёт сигнал от второй, а результат всё равно упорядочен по входу. Тесты не используют Thread.sleep и не требуют ускорения. Конкурентная версия может быть медленнее из-за накладных расходов, коротких задач или ограничений диска.

Показать на защите: отсутствующий файл между корректными, порядок TaskResult.index(), повторное использование executor после обработки и finally у владельца.
